PART 1

기능이 요구사항대로 동작하는가

직접 명령을 입력해서 확인하는 부분입니다. 아래 명령을 순서대로 입력하면 같은 결과를 볼 수 있습니다.

쉽게 말하면 : 커밋은 "사진 찍기", 브랜치는 "사진첩 이름표", HEAD는 "지금 펼쳐 둔 사진첩"입니다. 새 사진(커밋)은 펼쳐 둔 사진첩에만 붙습니다.

1-1

INIT을 하면 무엇이 만들어지나요?

main 브랜치를 만들고, HEAD를 main에 두고, 사용자 이름을 저장합니다.

  • 처음 만든 main은 아직 커밋이 없어서 None을 가리킵니다 (branches = {"main": None})
  • INIT을 다시 하면 기록은 그대로 두고 사용자만 바꿉니다. 여러 작성자 커밋을 만들어 SEARCH --author, LOG --sort-by=author를 확인하려고 이렇게 했습니다
  • INIT 전에 다른 명령을 하면 Not initialized. Use INIT <user_name> first
mini-git> init "Alice"
Initialized repository.
Current branch: main
Current user: Alice
mini-git> branch
* main -> (no commits)

1-2

브랜치를 바꾼 뒤 커밋하면 어느 브랜치에 붙나요?

COMMIT은 HEAD가 가리키는 브랜치의 이름표만 새 커밋으로 옮깁니다. 다른 브랜치는 그대로입니다.

  • branch feature : 지금 커밋을 가리키는 이름표를 하나 더 붙임 (커밋을 복사하지 않음)
  • switch feature : HEAD를 feature로 옮김
  • commit : 새 커밋의 부모 = 지금 커밋, 그다음 branches["feature"]만 새 hash로 바꿈
  • 출력의 [feature b348f02]와 branch 목록에서 main, feature가 다른 커밋을 가리키는 것으로 확인
mini-git> commit "Initial commit"
[main bda937b] Initial commit
mini-git> branch feature
Created branch: feature
mini-git> switch feature
Switched to branch: feature
mini-git> commit "Add login feature"
[feature b348f02] Add login feature
mini-git> branch
  main -> bda937b
* feature -> b348f02

LOG는 어떤 순서로 커밋을 보여 주나요?

1-4

PATH는 경로를 어떻게 찾고, 길이 없으면 어떻게 되나요?

연결을 방향 없는 선으로 보고 BFS로 선이 가장 적은 길을 찾습니다. 길이 없으면 None을 돌려주고 No path를 출력합니다.

  • login과 payment는 형제라서 부모(Initial commit)를 거쳐 갑니다
  • merge 뒤에는 merge 커밋을 거치는 길도 2칸이 됩니다. 길이가 같으면 hash1->hash2 글자가 사전순으로 더 작은 길을 고릅니다 (52b9683 < bda937b)
  • No path는 CLI에서 나오지 않습니다. 첫 커밋 말고는 모든 커밋에 부모가 있어서, 모든 커밋이 결국 첫 커밋과 이어지기 때문입니다. 그래서 연결이 끊긴 가짜 그래프로 테스트에서 확인합니다 (test_shortest_path_same_and_none)
  • 없는 hash를 넣으면 No path가 아니라 Unknown commit: ...
mini-git> path b348f02 27dd8e1
Path: b348f02 -> bda937b -> 27dd8e1
mini-git> merge feature
[main 52b9683] Merge branch 'feature' into main
mini-git> path b348f02 27dd8e1
Path: b348f02 -> 52b9683 -> 27dd8e1

2-2

hash로 커밋을 어떻게 빨리 찾고, hash가 겹치는 건 어떻게 막았나요?

dict(hash → Commit)로 평균 O(1)에 찾고, 새 hash가 이미 있으면 숫자(nonce)를 바꿔 다시 만들어 중복을 0개로 만듭니다.

  • dict는 key를 계산해서 칸 번호를 바로 알아내기 때문에 커밋이 많아도 찾는 시간이 거의 같음
  • hash 원본 = 카운터 | nonce | 메시지 | 작성자 | 시각. 카운터가 매번 달라서 같은 메시지, 같은 초여도 원본이 다름
  • SHA-1 앞 7자리만 쓰면 아주 드물게 겹칠 수 있음 → candidate not in self.commits로 확인하고, 겹치면 nonce + 1로 다시 계산
  • 테스트 : 같은 메시지로 2,000번 커밋해도 hash 2,000개가 모두 다름 (test_hashes_unique)
  • 다른 중복도 막음 : 같은 브랜치 이름 → Branch already exists, 역색인 같은 커밋 두 번 → _seen 집합으로 차단

2-3

역색인은 언제, 어떻게 갱신하나요?

커밋을 저장하는 바로 그 순간(_create_commit() 마지막 줄)에 두 색인을 같이 갱신합니다.

  1. 메시지를 공백으로 자르고 소문자로 바꿈 ("Add login feature" → add, login, feature)
  2. 단어마다 keyword_index[단어] 목록 끝에 hash 추가 (이미 있으면 건너뜀)
  3. author_index[작성자 소문자] 목록 끝에 hash 추가
  • COMMIT과 MERGE가 모두 _create_commit()을 지나서, 갱신하는 곳이 한 군데뿐 → 빠뜨릴 일이 없음
  • 커밋은 한번 만들면 바뀌거나 지워지지 않음 → 색인 수정, 삭제 코드가 필요 없음
  • 목록 끝에 붙이기만 하므로 결과가 자동으로 만든 순서대로 나옴

PART 3

개념을 설명할 수 있는가

알고리즘과 자료구조를 고른 이유에 대한 질문입니다. 단계별 애니메이션은 시각 가이드에도 있습니다.

쉽게 말하면 : 커밋 기록은 "족보"입니다. 족보는 부모 → 자식 방향으로만 이어지고, 내가 내 할아버지가 될 수는 없습니다. 이 성질 덕분에 순서대로 나열하고(LOG), 촌수를 세고(PATH), 조상을 찾을(ANCESTORS) 수 있습니다.

3-1

커밋 그래프는 왜 DAG이고, 순환이 생기면 뭐가 문제인가요?

부모는 항상 먼저 있고 커밋은 바뀌지 않아서 화살표가 과거로만 향합니다. 고리가 생기면 "누가 먼저인지"가 사라져 LOG, ANCESTORS가 성립하지 않습니다.

  • 방향 : 커밋을 만들 때 앞 커밋은 이미 있고 뒤 커밋은 아직 없음 → 앞 커밋만 가리킬 수 있음
  • 고리 없음 : 이미 있는 커밋만 부모로 삼고, 만든 커밋은 안 바뀜 → 따라가면 첫 커밋에서 끝남
  • 트리가 아님 : merge 커밋은 부모가 2개
고리가 생기면문제
LOGA가 B의 부모이면서 B가 A의 부모 → "부모 먼저"를 만족하는 순서가 없음. 출력할 수 있는 첫 커밋이 없어서 멈춤
ANCESTORSvisited가 없으면 같은 커밋을 계속 돌아 끝나지 않음. 있어도 "내가 나의 조상"이라는 말이 안 되는 결과
기록의 의미"이 변경이 저 변경보다 먼저"라는 역사가 성립하지 않음
직접 해 보기 : 고리를 만들면 위상 정렬이 어떻게 되는지

graph.py · topological_sort()의 raise ValueError("Commit graph has a cycle") / test_cycle_detected

3-2

LOG에서 부모를 항상 먼저 보여 주려고 어떤 방법을 썼나요?

Kahn 알고리즘으로 위상 정렬을 했습니다. "부모가 전부 출력된 커밋만 출력할 수 있다"는 규칙을 큐로 지킵니다.

  1. 커밋마다 "아직 출력 안 된 부모 수"를 셈 (처음엔 len(parents))
  2. 그 수가 0인 커밋(첫 커밋)을 큐에 넣음
  3. 큐에서 하나 꺼내 출력하고, 그 자식들의 수를 1씩 뺌
  4. 0이 된 자식을 큐에 넣음 → 큐가 빌 때까지 반복
  • merge 커밋은 부모 둘이 다 출력돼야 0이 되어 큐에 들어감
  • 시각 순으로 하지 않은 이유 : 같은 초에 만든 커밋이 많아서 (1-3의 출력 참고)
  • O(V + E) : 커밋 하나, 연결 하나를 한 번씩만 봄
  • list.pop(0)은 뒤 원소를 전부 당겨서 O(N) → deque.popleft() O(1) 사용

3-3

PATH에 BFS를 쓴 이유와, 연결을 방향 없이 본 이유는요?

BFS입니다. 모든 선의 길이가 1인 그래프에서는 BFS가 처음 닿은 거리가 곧 최단 거리입니다. 무방향은 과제 요구이고, 그래야 형제 커밋 사이 거리를 잴 수 있습니다.

  • BFS는 1칸 거리를 전부 본 다음 2칸 거리를 봄 → 먼저 닿은 길이 가장 짧은 길
  • 방향을 지키면 자식 → 부모로만 갈 수 있음 → login에서 payment(형제)로 갈 길이 없음
  • 무방향이면 "login → Initial → payment"처럼 위로 갔다가 내려올 수 있음 → "두 커밋이 몇 칸 떨어져 있나"를 셀 수 있음
  • 동률 처리 : 도착점에서 BFS로 "남은 칸 수"를 먼저 구하고, 출발점부터 남은 칸이 1 줄어드는 이웃 중 hash가 가장 작은 쪽으로 감. hash 길이가 모두 7자라 이렇게 고르면 경로 글자 전체도 사전순 최소
  • O(V + E)

3-5

역색인은 왜 전부 훑는 검색보다 빠른가요?

순회는 검색할 때마다 모든 커밋 메시지를 읽지만(O(N × L)), 역색인은 커밋할 때 미리 적어 둔 목록을 dict에서 한 번에 꺼냅니다(평균 O(1) + 결과 수 K).

  • N = 커밋 수, L = 메시지 길이, K = 찾은 커밋 수
  • 책 비유 : 순회 = 처음부터 끝까지 넘기며 단어 찾기, 역색인 = 책 뒤 찾아보기에서 쪽 번호 바로 보기
  • dict가 O(1)인 이유 : key를 hash 계산해서 저장 칸 번호를 바로 알아냄 → 커밋이 몇 개든 칸을 찾는 시간은 같음
  • 대가 : 커밋할 때 단어 수만큼 일을 더 함(O(단어 수)), 메모리를 더 씀. 검색이 커밋보다 훨씬 자주 일어나면 이득
  • 직접 잰 값 (커밋 10,000개, 이 노트북) : 역색인 0.44ms, 전부 훑기 2.17ms

작성자 정렬에서 부모 먼저 순서도 지켜야 한다면요?

위상 정렬의 큐를 "작성자 이름이 가장 작은 것부터 나오는 우선순위 큐"로 바꿉니다. 부모가 다 나온 커밋들 중에서만 작성자순으로 고르는 방식입니다.

  • 지금 방식(위상 정렬 → 작성자로 병합 정렬)의 문제 : Bob이 만든 부모보다 Alice가 만든 자식이 앞에 나올 수 있음 (아래 데모 왼쪽)
  • 바꾼 방식
    1. Kahn 알고리즘 그대로 "남은 부모 수"를 셈
    2. 남은 부모 수가 0인 커밋을 최소 힙(가장 작은 값이 항상 맨 위에 오는 구조)에 넣음. 기준 = (작성자 소문자, 생성 순번)
    3. 힙에서 꺼낼 때마다 지금 고를 수 있는 커밋 중 작성자가 가장 앞인 것이 나옴
  • "부모 먼저"가 1순위, 작성자순은 2순위 → 완벽한 작성자순은 아닐 수 있음 (그게 이 요구사항에서 가능한 최선)
  • 시간복잡도 O((V + E) log V)
  • 정렬 라이브러리 금지 조건이 있어서 heapq 대신 힙을 직접 구현하는 게 안전
